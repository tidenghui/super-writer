# 引擎设计

> 这份文档记录的是**为什么**这样做，不是怎么用。用法看 README。

## 三个基本判断

### 1. 瓶颈是判断力，不是产出速度

调度器、队列、重试、并发——这些几天就能写完，不是护城河。

真正难的是：**模型能写出「还不错的一章」，但写不出「三十万字之后仍然成立的一本书」。** 角色口吻漂移、伏笔埋了不回收、设定前后矛盾、中段节奏塌方——这些是叙事学问题。

所以引擎的算力预算里，**写只占 1/3，剩下 2/3 全部花在「判断这一章行不行」上。**

### 2. 读者反馈是滞后信号

「质量由读者反馈决定」是对的，但读者是**用弃书投票**的。等他投完票，你已经写完 15 章了。

所以必须分层：

| 层 | 信号 | 延迟 | 作用 |
|---|---|---|---|
| 冷读预测 | 机器模拟读者：会不会点下一章 | 秒 | 每章放行前拦截 |
| 内部批评 | 五个专职批评家 | 分钟 | 定点修缮 |
| 真实读者 | 追读率、弃书点、评论 | 天 | 唯一有资格定义「好」 |

前两层不是为了替代第三层，是为了**给第三层争取时间**。

冷启动期没有读者，第三层是空的。这时候你和内部批评家顶替它——但引擎必须写成「信号可插拔」的样子，等有人读的时候能直接接上。

### 3. 中文网文是可工程化的

纯文学没法工程化，它的好是「无法预判的意外」。

但网文有成熟的工业标准：黄金三章、每章 2000–3000 字、章末必留钩子、三章一小高潮、十章一中高潮。这些节拍本来就是表格。

**我们挑战的不是文学创作，是一条有明确合格线的类型小说生产线。**

## 一个夜晚的时刻表

现在还是手动触发，这是它最终该有的样子：

```
02:00  全书重读审计
       把已写的全部章节重读一遍，只输出「漂移报告」：
       口吻变形 / 设定冲突 / 事实矛盾 / 逾期未还的债 / 重复桥段
       —— 这是人类编辑最费神、也最有价值的一件事

02:20  规划       把大纲拆成场景，每个场景必须有转折
02:50  开场 ×4    不同切入方式，由一个挑剔编辑选出最好的
03:30  起草       + 五个批评家并行开火
04:30  定点修订   只改被点名的句子
05:30  终审       不过线打回，最多三轮
07:00  发布
```

五小时机器时间换一章。这不是浪费——**时间是唯一可以买品质的东西。**

## 判据（gate）

一章要放行，三条同时满足：

1. 没有 `blocker` 级缺陷
2. 五个批评家的平均分 ≥ 7.5
3. 三个冷读分身里至少两个说「会点下一章」

不满足就修订，最多三轮。最后用**分数最高的那一版**，而不是最后一版——修订有时会改坏。

## 两个防作弊机制

### 批评家必须逐字引用

`critics.ts` 里的 `verifyQuotes()` 会检查每条缺陷的 `quote` 是否真的出现在正文里。引用不到的，直接作废并计数。

不加这一条，模型会写出一堆「人物略显单薄」这种既对又没用的话，然后你花三次调用去修一个不存在的问题。

### 写手和批评家必须不同源

同一个模型审自己的稿，盲区完全重合——它会真诚地认为自己的平庸句子很好。

`npm run doctor` 会检查这一点。目前只配了 DeepSeek 一家，所以是「同族但不同模型」（chat 写、reasoner 审），这是**打折的**多样性。配第二个厂商（Kimi / GLM / 通义）质量会有可感知的提升。

## 故事圣经为什么是文件而不是数据库

创作侧用文件，阅读侧用数据库。

- 圣经是**人也要读要改**的东西，Markdown / JSON 能用 git 看 diff，能在编辑器里直接改
- 事实和伏笔是引擎读写的，用 JSONL 追加，可回溯
- 等有了读者，章节、评论、埋点才需要数据库

把创作产物放进数据库的唯一后果是：你不敢改，也看不懂。

## 算力要偏心地分配

一本书的生死在前三章。第 1 章留不住人，后面写得多好都没人知道。

引擎必须允许**不对称预算**：
- 第 1–3 章：开场候选 ×8，修订轮数 ×3，反复冷读
- 第 4 章之后：标准档

已实现（`profileFor`）：第 1–3 章开场候选 ×8、修订 3 轮、要求冷读 3/3 全票；第 4 章起降到 ×4 / 2 轮 / 2 票。

另外 `--candidates K` 可以让同一章跑 K 个变体（温度 0.90 / 0.95 / 1.00 …），比完再落盘。第一章值得这么干。

## 调参实录（2026-10，第一章，¥9 换来的）

这些是实测结论，不是推测。改引擎之前先读一遍。

### 1. `reasoning_effort` 会反向咬人

想压低批评家的思考量，加 `reasoning_effort: "low"`——结果推理量从 0 涨到 8k–23k 字，
耗时从 6 秒涨到 28 秒，内容还是被截断的空字符串。

对照实验（同一份真实审稿 prompt）：

| 配置 | 耗时 | 输出 token | 推理字数 | 结果 |
|---|---|---|---|---|
| reasoner + low | 32s | 5000（截断） | 16342 | JSON 坏 |
| chat + low | 28s | 5000（截断） | 7832 | JSON 坏 |
| **chat + 不传该参数** | **6s** | **789** | **0** | **JSON 好** |
| reasoner + 不传 | 36s | 5923 | 16333 | JSON 好 |

结论：**不要传 `reasoning_effort`**。`deepseek-reasoner` 永远推理，`deepseek-chat` 不传该参数时零推理。
现在只有 planner / auditor 用 reasoner，其余全部 chat。

### 2. 缺陷条数不能当闸门

五个批评家，每个写 5–6 条意见，一章就是 30 条。曾经用「均分 ≥7.5」「blocker ≥1 就拦」，
结果**没有任何一章能过**，而且每轮修订都在增加 blocker（5→3→1→2→4 震荡）。

批评家是被要求挑刺的，6 分意味着「合格但有毛病」。现在闸门是：

- 冷读票数达标（这是唯一和「读者愿不愿意翻页」直接挂钩的指标）
- 最低分 > 3
- 打 4 分以下的不超过 1 位
- blocker ≥ 5 才拦

### 3. 修订的边际收益是负的

整章重写修订：每修一处带进三处新错，均分 6.6 → 6.4 → 5.8。
改成补丁式（模型只输出「原文片段 → 改文片段」，引擎机械替换，找不到就跳过）后不再伤及无辜，
但**评分仍然在降**（6 → 5.7 → 5）。

所以：黄金三章改为「独立多跑几版再挑」（`--candidates 3`），修订只留一轮兜底，
并且一旦发现修订后变差就回退。

### 4. 批评家会按写实标准杀死超自然设定

第一章的核心钩子是「十七年前的陈血还是湿的」。三个批评家连续两轮把它当物理错误要求修改。

补丁：在 `premise.md` 里写一节「允许的异常」，并让**所有**批评家都读到前提
（之前只有连续性编辑能看设定）。判断标准改成「主角有没有察觉到不对劲」——
察觉到了就成立，毫无反应才是 bug。

## 已知的坑

1. **自己评自己**：批评家和写手同厂商，相关性太高。缓解：异厂商、不同 rubric、要求引用原文。
2. **修订跑偏**：模型修 A 的时候顺手把 B 也改了。缓解：明确「没被点名的地方一个字都不要动」，并且保留最高分版本。
3. **冷读分身说客套话**：三个分身都是同一个模型，可能都高估。缓解：人格差异要做足（老书虫 / 通勤读者 / 解谜读者的判断标准确实不同）。
4. **长程一致性靠不住**：等到 20 章以后，靠摘要 + 事实表可能不够。那时候要上向量检索或分级摘要。
5. **「AI 写的」是减分项**：读者不在乎谁写的，只在乎好不好看。所以对外不需要强调引擎，只需要强调故事。

## 第一章实测成绩（2026-10-23）

| 指标 | 结果 |
|---|---|
| 耗时 | 2 分 10 秒（8 个开场候选 → 起草 → 5 批评家 → 3 冷读 → 放行） |
| 成本 | ¥0.31 |
| 字数 | 2135 |
| 冷读 | 3/3 说会点下一章 |
| 批评家均分 | 6.4（最低 6） |
| 修订轮次 | 0（第一轮就过线） |

批评家提出的有效问题（供下一轮改 prompt 用）：
- 主角直接用手刮血痂，缺乏「能不能碰」的犹豫，与他的谨慎不一致
- 老周说出「那册书是我爹抄的」——违反「禁言」设定，他不能直白陈述
- 「气感」「引气」这类词不该出现在抄书匠的叙述里
