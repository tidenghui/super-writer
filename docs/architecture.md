# 架构说明与三个待定项

写在 2026-10-27。回答三个问题：写作流程是什么、项目该怎么拆、书该存在哪里。

---

## 零、现状

```
super-writer/
  src/
    engine/     写作引擎（出题、章纲、章节流水线、批评家、归档）  ~3600 行
    serve/      阅读器（SSR、目录、RSS、静态资源）               ~500 行
    canon/      一本书的文件格式与读写                           ~500 行
    ops/        访问统计                                          ~280 行
    cli.ts      所有命令的入口                                    ~700 行
  books/        数据：11 部书、每部的 bible/ chapters/ canon/
  config/       模型路由与价格
  deploy/       systemd / Caddy / 推送 / 备份
  ops/  docs/   运营台账与文档
```

**问题**：三层职责混在一个 `src/` 里，阅读器和写手共用 `canon/store.ts`
和 `engine/config.ts`，没法分别部署、分别给别人用。

## 一、写作流程与角色

### 一本书的生命周期

```
① 出题       人给「一句种子 + 一句结局方向」
              ↓
② 圣经       引擎生成 premise / world / style / 人物 / 卷纲 / 章节目录
              ↓
③ 全书章纲   逐章扩成 5–8 个场景级节拍（带前置条件、出场人物、第几天、埋/还哪条债）
              ↓
④ 逐章写作   ← 下面详述，这是最重的一段
              ↓
⑤ 归档       每章定稿后沉淀：摘要、事实、伏笔、角色特征、禁忌、物件、数量账本
              ↓
⑥ 发布       通过闸门即可见；未定稿或未到发布点的章，连同后面一起不对外
```

### 一章的流水线

```
规划 planner（deepseek-reasoner）
  拆 3 个场景：目标 / 阻力 / 转折 / 出场 / 字数配额
      ↓
规划复审 showrunner
  拒绝「他去了，就拿到了」的流水账；不过就重排
      ↓
候选开场 opener（黄金三章 8 个候选，之后 4 个）
  → showrunner 选出最好的一个
      ↓
起草 writer
  按场景写正文；字数不够就补写一次
      ↓
机械体检（代码，不问模型）
  禁用词 / 失声 / 长句 / 情绪直陈 / 引号配对 / 角色串味 / 重复解释 / 越界发言
  → 命中就交给 reviser 定点清洗
  → 引号再做一次确定性修复（栈扫描，不靠模型）
      ↓
五批评家（并行，deepseek）
  连续性 / 角色一致性 / 节奏 / 逻辑 / 文风　各打分并给缺陷
      ↓
三读者分身（并行，盲读：只给前情和本章）
  老书虫（gpt-6-luna，最严格）· 通勤读者 · 解谜读者
      ↓
放行判定（代码）
  冷读票数 ≥ N　且　最低分 > 3　且　4 分以下不超过 1 个　且　硬伤 < 阈值
      ↓
边际情况 → 仲裁 arbiter（gpt-6.1-sol）
  只回答一句：这些毛病会不会让读者出戏
      ↓
修订 reviser
  打补丁（find/replace，逐字唯一匹配），仲裁意见优先级最高
  修完反而更差 → 回退到上一版
      ↓
复审一轮 → 仍不过则整章重来（最多 12 次，每 3 次重排这一章的章纲）
      ↓
定稿 → 归档 → 立即可见
```

### 十三个角色

| 角色 | 干什么 | 模型 |
|---|---|---|
| **showrunner** | 出题、规划复审、开场评选 | deepseek-chat |
| **planner** | 把章纲拆成可写的场景 | **deepseek-reasoner** |
| **opener** | 生成开场候选 | deepseek-chat |
| **writer** | 写正文 | deepseek-chat（可换） |
| **reviser** | 定点打补丁 | deepseek-chat |
| **critic** | 五个批评家（同一角色，五种视角） | deepseek-chat |
| **coldReader** | 读者分身 | deepseek-chat |
| **coldReaderStrict** | 最严格的读者（老书虫） | **gpt-6-luna** |
| **outlineReview** | 章纲复核：有没有违反已写事实、依赖不存在的东西 | **gpt-6.1-sol** |
| **arbiter** | 终审：这一章现在能不能发 | **gpt-6.1-sol** |
| **auditor** | 全书审计：跨章漂移 | **gpt-6.1-sol** |
| **canonRecorder** | 归档：事实、伏笔、特征、规则、物件、账本 | deepseek-chat |
| **summarizer** | 章节摘要 | deepseek-chat |

**分工原则**：写和改用便宜的（高频、量大）；判断用贵的（低频、决定性）。

## 二、项目拆分：两个子项目

### 目标

```
tidenghui/
  packages/
    contract/     一本书的文件格式（类型 + 读写）—— 唯一的共享契约
    writer/       出题、章纲、章节流水线、批评家、归档
    reader/       阅读器、目录、RSS、统计
  books/          数据
  ops/ deploy/ docs/
```

### 为什么这样切

**阅读器和写手唯一真正共享的东西，是「一本书长什么样」**——文件格式和目录约定。
只要把这层抽成 `contract`，两边就可以各自独立：阅读器可以部署到别处，写手可以跑在另一台机器上。

现在两者还偷偷共享了 `engine/config.ts`（里面有个 `bookDir`）。这是唯一要拆的耦合点。

### 分三步走，每步都能跑

| 步骤 | 做什么 | 风险 |
|---|---|---|
| **1** | 抽出 `packages/contract`（类型 + store 的读写），两边改成依赖它 | 低，纯搬文件 + 改 import |
| **2** | `src/engine` → `packages/writer`，`src/cli.ts` → writer 的入口 | 低 |
| **3** | `src/serve` → `packages/reader` | 低 |

用 npm workspaces 管，保留根目录的一条 `npm run` 入口，部署脚本不用改。

### 不建议现在做的

- **不要拆成两个 git 仓库**。现在拆，改动成本比收益大。先在一个仓库里分目录，等真的需要分别开源/协作再拆。
- **不要给阅读器加构建步骤**。它现在是零依赖 SSR，改版快、抗故障，这是优点。

## 三、存储：GitHub 行不行

### 行，但要先想清楚三件事

**① 剧透**

`bible/` 里有：完整大纲、每一章的节拍、伏笔账本、结局方向。
**这些一旦公开，读者被剧透得干干净净。**

所以公开的部分只能是 `chapters/`（正文）和 `book.json`（书名、简介、题材）。
`bible/` 和 `canon/` 必须私有。

**② GitHub 不能当运行时存储**

它适合做"源和备份"，不适合做"线上读取"：有速率限制、延迟不可控、可用性不受我们控制。

正确形态是：**服务器上有本地副本（现有架构不变），GitHub 是它的同步与备份。**

**③ 提交粒度**

每章定稿 → 一个 commit：

```
chore(b01): 第 12 章《做不出的那道菜》

评分 6.2 · 冷读 3/3 · ¥0.43
```

历史即写作过程，这和你说的"写作过程就是提交过程"完全一致。

### 三种方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 一本一仓库** | 每本书一个 repo | 干净、可 fork、可单独授权 | 20+ 个仓库要管理；跨书更新（目录、封面）麻烦 |
| **B. 一个图书馆仓库** | 一个 repo，每本一个目录 | 只需管一个仓库；整体原子更新 | 单个书的 star/issue 不明显 |
| **C. 私有备份 + 公开镜像** | bible 私有，正文另外公开 | 不剧透；开放 | 两套同步逻辑 |

### 我的建议

**先做 C 的第一步：把 `books/` 整体每章同步到一个私有仓库。**

理由：
- 成本几乎为零，解决的是"数据丢了怎么办"这个真实风险
- 不剧透、不改架构、不动线上读取路径
- 之后想公开，只需要再推一个只含正文的仓库，或者把私有仓库的部分目录公开

**不建议现在就按"一本一仓库"落地**，因为 20 个仓库的运维成本（建仓、授权、备份、同步）会立刻压过来，而它解决的问题——"开放"——用 B 或 C 都能解决。

---

## 四、建议的顺序

如果按性价比排：

1. **先做存储备份**（半天）：`books/` 每章提交到私有 repo。解决最要命的风险，几乎零成本。
2. **再做流程文档**（已完成，就是这份）：让后面所有改动有共同语言。
3. **最后做项目拆分**（1–2 天）：`contract` / `writer` / `reader` 三分。它是"能力"，不是"当务之急"。

**理由**：现在的瓶颈是内容和分发，不是代码结构。拆分是为了将来能分别演进，不是为了让今天跑得更快。

## 五、需要你拍板

1. **拆分顺序**：先 `contract` 再两个包，还是你希望先看到目录结构？
2. **存储**：先做私有备份（推荐），还是直接上"一本一仓库"？
3. **公开程度**：正文公开、bible 私有——这个边界你认可吗？
